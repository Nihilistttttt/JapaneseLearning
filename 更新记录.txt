【更新13】XML inflate替换为代码创建
日期：2026-07-29
涉及文件：WordComponentView.java, Select.java, 优化清单.txt

问题：
  WordComponentView.initComponents中每个汉字组件都调用LayoutInflater.inflate()加载XML布局，
  涉及XmlPullParser解析+反射创建View对象。每个词平均3-5个汉字组件，每个例句约5-10个词，
  一页面约218个inflate调用。XML inflate比直接代码创建慢3-5倍（XML解析+属性查找+反射开销）。

  更关键的是：XML中定义的textSize被configureTextViews立即覆盖，XML中的marginStart/marginEnd
  全部为0dp（dimens.xml确认），被configureMargins动态计算覆盖。XML布局完全是冗余的中间层。

解决方案：
  1. initComponents改为直接new LinearLayout(vertical, center_horizontal) + new TextView(kana) + new TextView(kanji)
  2. 设置bold typeface、includeFontPadding=false、textColor=md_on_surface等XML中定义的属性
  3. setText/setTextSize由代码直接设置（原configureTextViews内联）
  4. 删除configureTextViews方法（不再需要findViewById）
  5. Select.layoutParams移除layout_1/layout_2/kanji_id_1/kanji_id_2/kana_id_1/kana_id_2共6个字段及getter
  6. Select.selectLayout移除R.layout/R.id分支和R import

效果：
  - 每个汉字组件省去一次XML inflate（XmlPullParser+反射），改为3个直接构造函数调用
  - Select.layoutParams从12个字段精简到6个字段
  - Select.selectLayout从30行精简到15行
  - 6个XML布局文件(view_*char.xml)不再被运行时引用（可保留供设计预览用）

意义：
  - XML inflate是Android渲染管线的已知性能瓶颈，Google官方也推荐热路径用代码创建
  - 消除"XML定义→代码覆盖"的冗余中间层，逻辑更清晰
  - 为后续进一步优化（如TextView预分配池）扫清障碍

新理解：
  - XML布局中定义的textSize/margin全被代码覆盖，XML仅充当View结构模板
  - 当XML属性全部被代码覆盖时，XML inflate就是纯粹的浪费
  - Select.layoutParams的layout/kanji_id/kana_id字段只为XML inflate服务，代码创建后完全不需要

【更新12】Paint对象复用优化
日期：2026-07-29
涉及文件：SentenceView.java, WrappedPhraseView.java, BasicWordView.java, 优化清单.txt

问题：
  measureWordWidth/measureCharWidthPx/calcMarginPx/estimateWordWidth每次调用都new Paint()+setTypeface()+setTextSize()，
  而这些方法在渲染热路径中被频繁调用（每个例句约10-15次measureWordWidth，每个WrappedPhrase约5-8次measureCharWidthPx）。
  Paint对象创建涉及Native层Skia资源分配，反复创建产生不必要的GC压力。

解决方案：
  1. SentenceView：字体大小在构造时由layoutParams确定，之后不变 → 提取kanjiPaint/kanaPaint为成员变量，构造时初始化createPaint()，measureWordWidth/calcMarginPx直接使用
  2. WrappedPhraseView：同理，kanjiPaint/kanaPaint为成员变量
  3. BasicWordView：estimateWordWidth在while循环中currentLevel--改变字体大小 → 静态SparseArray<Paint>缓存，key=Math.round(textSizePx)，跨实例复用

效果：
  - SentenceView：每个实例从N次new Paint()降为2次（构造时）
  - WrappedPhraseView：每个实例从N次new Paint()降为2次（构造时）
  - BasicWordView：跨所有实例，相同textSizePx的Paint只创建一次（7档字体最多14个Paint对象）
  - measureWordWidth签名简化：移除不再需要的wordId参数

意义：
  - 热路径中消除不必要的对象创建是Android性能优化的基本实践
  - Paint对象持有Native Skia资源，复用减少GC压力和Native内存分配

新理解：
  - SentenceView/WrappedPhraseView的字体大小在构造时确定不变，适合成员变量方案
  - BasicWordView的while循环中字体大小变化，但7档字体最多7种textSize，SparseArray缓存是最佳方案
  - SparseArray<Paint>用int key比HashMap<Float>更高效（避免autoboxing），textSizePx四舍五入到int精度足够

【更新11】逐类提取基类消除重复代码
日期：2026-07-29
涉及文件：WordComponent.java, CorrespondingWord.java, PhraseComponent.java(新增),
  BasicWord/AntonymWord/SynonymWord/ConjugationForm/Idiom/KanjiFormWord/UsageDistinction/WordSentence/WordCollocation.java(9个JavaBean),
  WordComponentListView.java(新增), AntonymWordView/SynonymWordView/KanjiFormWordView.java,
  WordViewFragment.java(新增), 9个ViewFragment,
  ConverterHelper.java(新增), 13个Converter,
  优化清单.txt

问题：
  各类之间结构高度相似却未利用Java继承/泛型/接口机制，导致约970行重复代码：
  1. JavaBean: getCompositeKanji/Kana重复5次，hasComponentCountMatch重复3次，validateComponents重复3次，deepCopy/deepUnmodifiable重复2次
  2. WordView: AntonymWordView/SynonymWordView/KanjiFormWordView三者的构造初始化+initViews循环+margin计算逻辑完全相同(95%相似)
  3. Fragment: 9个Fragment的ViewModelProvider获取+subFontLevel读取+容器添加逻辑完全相同
  4. Converter: null检查+try/catch+日志模式重复26次，8个Converter声明了未使用的Gson实例

解决方案：
  1. JavaBean继承体系：WordComponent抽象基类(wordId+kanjiComponents+kanaComponents+getCompositeKanji/Kana+hasComponentCountMatch+unmodifiableListOf+validateComponentsNotEmpty)，CorrespondingWord extends WordComponent(+correspondingWordId)，PhraseComponent抽象基类(嵌套List结构+deepCopy+deepUnmodifiable+validatePhraseComponents)，9个JavaBean改为extend对应基类
  2. WordView泛型基类：WordComponentListView<T extends WordComponent>，提取构造初始化+initViews循环+applyFirstComponentMargin，子类只需实现getClickId(T)一个方法
  3. Fragment泛型基类：WordViewFragment<T>，提取onCreateView+onViewCreated中的ViewModelProvider获取+subFontLevel读取+容器添加，子类只需实现createContentView()一个方法
  4. Converter工具类：ConverterHelper静态类(entityToModel+modelToEntity泛型方法，用Function+Supplier消除样板)，13个Converter移除未使用Gson+DEFAULT内联化

效果：
  - 43 files changed, +1078 / -1282, 净减1026行
  - 新增同类组件只需实现1个抽象方法，而非复制粘贴整套逻辑
  - 外部API无变化，所有公共方法签名保持不变

意义：
  - 重复代码是维护的敌人：改一处漏一处是最常见的bug来源
  - 继承/泛型是Java的核心OOP机制，项目之前完全未利用，这是架构层面的改进
  - 为后续新增词性类型(如DerivedForm)提供了可复用的基类框架

新理解：
  - Java Builder与继承不兼容：Builder是静态内部类，不参与继承链，因此基类只提取公共字段和方法，Builder保持各子类独立
  - 泛型Fragment(WordViewFragment<T>)中T是元素类型而非List<元素>，data字段已是List<T>，子类写WordViewFragment<AntonymWord>而非WordViewFragment<List<AntonymWord>>
  - ConverterHelper用Function<E,M>+Supplier<M>比抽象基类更轻量：保持静态方法API不变，调用方无需修改

【更新10】字体大小重构：7档线性插值+弹窗选择+UI优化
日期：2026-07-27
涉及文件：Constants.java, Select.java, LearnPageStateViewModel.java, LearnPageToolBar.java,
  MainLearnPageFragment.java, 7个Fragment, ReviewPage.java, BasicWordView.java,
  MeaningView.java, SentenceView.java, CollocationView.java, WordComponentView.java,
  WordListAdapter.java, fragment_extended_meaning.xml, fragment_main_learn_page.xml

问题：
  1. 旧3档字体(SMALL/NORMAL/LARGE)粒度太粗，用户无法精细调节
  2. 循环切换(cycleFontSize)交互差，无法直观选择目标档位
  3. 主词区和子区域(释义/例句/搭配)共用一个fontLevel，无法独立控制
  4. 弹窗内词头大小与主页面不一致，释义换行不自然，例句区域无圆角卡片
  5. SentenceView文字宽度估算用sp×字符数模型，7档插值后偏差大导致换行溢出
  6. calcMarginPx异号分支(假名宽-汉字宽<0)从未生效，marginPx>0过滤了负值

解决方案：
  1. 7档线性插值(0-6)：FONT_SIZE_SMALL=0, FONT_SIZE_NORMAL=3, FONT_SIZE_LARGE=6
     - 主词区范围：kanji 8-32sp, kana 4-16sp
     - 子区域范围：definition 12-17sp
     - Select.selectLayout()连续插值，XML布局按档位映射(0-1→small, 2-3→normal, 4-6→large)
  2. 弹窗选择器：点击工具栏字体按钮弹出PopupWindow
     - "词头大小"/"其他大小"两组7个离散按钮(1-7)
     - 选中深蓝底白字，未选中白底蓝边蓝字，实时调用setWordFontLevel/setSubFontLevel
  3. 双独立level：wordFontLevel/subFontLevel各自MutableLiveData+SharedPreferences持久化
     - 子区域Fragment获取subFontLevel，主词区Fragment获取wordFontLevel
     - 删除旧fontSizeLevel/cycleFontSize/@Deprecated方法
  4. UI优化：
     - 词头居中：word_container加gravity=center_horizontal，BasicWordView改WRAP_CONTENT
     - 弹窗95%屏宽水平居中，Y轴跟随点击词+8dp偏移，去掉标题，词头用wordFontLevel
     - 例句区域CardView圆角包裹(12dp)，释义Flow流式换行，弹窗模式不限行
     - 释义弹窗间距优化(日文12dp顶，例句12dp左右+4dp顶+8dp底)
  5. 文字宽度精确测量：Paint.measureText()+DEFAULT_BOLD替代sp×字符数
     - estimateWordWidth/estimateCharWidthPx改为Paint测量，正确sp→px转换
     - BasicWordView.estimateWordWidth同步修改
  6. calcMarginPx修复：
     - 改为kanaPaint.measureText()-kanjiPaint.measureText()，可产生负值
     - marginPx>0改为marginPx!=0，负margin正确应用

效果：
  - 7档精细调节，词头和子区域独立控制
  - 弹窗直观选择，不再循环切换
  - 例句换行准确，不再溢出
  - 异号margin生效，假名宽→汉字宽过渡更自然

意义：
  - 字体大小是阅读体验的核心，3档→7档是质的提升
  - 独立控制满足不同用户对词头/释义的不同偏好
  - Paint.measureText()是Android文字渲染底层，比sp×字符数模型根本性更准确

新理解：
  - Paint.measureText()和TextView渲染用同一字体引擎(Skia/HarfBuzz)，对CJK字符误差<1px
  - 旧估算bug本质：把sp值当dp用(kanjiLength*kanjiSize然后dpToPx)，sp和dp在非1.0字体缩放下不等
  - calcMarginPx异号分支从初始提交就是死代码：marginPx>0过滤了所有负值
  - FlowLayout适合释义流式排列，但例句换行需要标点前瞻/单词内拆分等复杂逻辑，不适合用FlexboxLayout替代

【更新9】例句换行优化：单词内拆分+跨行高亮联动+标点前瞻预留
日期：2026-07-26
涉及文件：SentenceView.java, WordComponentView.java

问题：
  1. 例句换行时整个单词换到下一行，即使只差一两个字符也整词换行，空间浪费严重
  2. 闭合标点（。、！？」等）放不下时留在当前行溢出，视觉不美观
  3. 拆分后的单词两部分没有高亮联动，点击一部分只高亮该部分

解决方案：
  1. 单词内拆分：放不下时按组件粒度拆分WordComponentView，part1留当前行，part2换新行
     - isSplittableWord(): 共享假名组件（如貴方→['貴方']/['あなた']）不拆分
     - findSplitPoint(): 逐字符累加宽度找拆分点
     - 不可拆分词仍整个换行
  2. 跨行高亮联动：WordComponentView新增linkedView机制
     - setLinkedView(): 双向绑定两个拆分部分
     - setPressed()重写：同步linkedView的pressed状态，isSyncingPress防递归
     - drawableStateChanged()重写：同步刷新linkedView的Drawable
  3. 标点前瞻预留：处理单词时前瞻下一个token是否闭合标点
     - 如果是，将标点宽度+词与标点间margin计入换行判断(punctReservePx)
     - remainingPx也减去punctReservePx，确保拆分后part2后面留有标点空间
     - 标点自然跟在单词后面，不会孤零零出现在行首
  4. 间距计算重构：去掉indexed lists(firstKanjiLengthList等)，改用prevLastKanji/prevLastKana追踪
     - 提取calcMarginPx()独立方法，消除重复代码

效果：
  - 长单词可拆分跨行显示，空间利用率大幅提升
  - 闭合标点不再溢出或孤立在行首
  - 拆分单词两部分高亮联动，点击任意部分整体高亮

意义：
  - 例句是日语学习最核心的展示内容，换行质量直接影响阅读体验
  - 标点不换行首是日文排版的基本规范
  - 跨行高亮联动保证拆分后单词的交互一致性

新理解：
  - 单词内换行比回溯移除View简单得多——前瞻预留空间，标点自然跟随
  - linkedView双向绑定需注意递归：isSyncingPress标志确保setPressed只传播一层
  - 共享假名词（多汉字共享一个假名注音）不能拆分，否则假名注音无法正确居中

【更新8】非英文释义彻底过滤
日期：2026-07-25
涉及文件：jmdict_to_room.py, generate_room_db.py, WordDatabase.java, room_import.json, word_database.db

问题：
  释义界面只有第一个卡片是英文的，其余是德语/法语/西班牙语/俄语等。
  之前的"英文过滤"只在DB层面用ijson更新了translationDefinition字段，但：
  1. originalDefinition仍然包含所有语言的gloss
  2. 每个sense都创建了WordMeaning，包括没有英文gloss的sense
  3. 重新生成DB时room_import.json中仍有非英文数据

根因：
  jmdict_to_room.py第384行 `if not eng_glosses: eng_glosses = [g for g in glosses if g.get('text')]`
  这个fallback把非英文gloss当作英文释义写入了originalDefinition

解决方案：
  1. 跳过没有英文gloss的sense，不创建WordMeaning（continue而非fallback）
  2. 重新运行jmdict_to_room.py生成新的room_import.json
  3. 重新运行generate_room_db.py重建DB

效果：
  - WordMeanings从676547降到252393（去掉62%非英文释义）
  - DB从120.2MB降到72.4MB
  - 彼の：6个meaning→1个（只保留英文"that; those; the"）
  - 彼：11个meaning→6个（只保留英文释义）
  - 抽查1000条无任何非英文内容

意义：
  - 释义是用户最核心的交互界面，非英文释义对中文用户毫无价值且造成困惑
  - 每个释义卡片应对应一种意思的进一步展开，与单词页面可跳转的释义一一对应

新理解：
  - JMDict的sense结构：每个sense可能只包含一种语言的gloss，不同语言的翻译被分到不同的sense中
  - 之前以为一个sense包含多种语言gloss是误解——实际上JMDict为每种语言创建独立的sense
  - room_import.json是数据的源头，任何修改都必须从源头重新生成，不能只改DB

【更新7】例句假名注音修复：多汉字合并 + reading拆分 + 混合变形处理
日期：2026-07-25
涉及文件：extract_sentences.py, generate_room_db.py, add_sentences_to_db.py, WordDatabase.java, word_sentences_data.json, word_database.db

问题：
  1. 多汉字词共享假名时，假名只放在第一个汉字头上（如"貴方"的"あなた"只在"貴"上方），不居中
  2. EDRG复合词/短语的reading被整体当作第一个汉字的注音（如"帽子を取る"的"ぼうしをとる"全放在"帽"上）
  3. {xxx}含汉字的变形形式（如{帰った}、{面白かった}）处理不当——要么被当作假名变形走derive导致乱码，要么reading无法正确拆分

解决方案：
  1. _merge_shared_kanji_kana(): 后处理步骤，将连续汉字+只有第一个有假名的情况合并为一组
     - 貴方→['貴方']/['あなた']，渲染时"あなた"自然居中在"貴方"上方
     - 有逐字注音的词不受影响（如日本語→['日','本','語']/['に','ほん','ご']）
  2. _split_reading_by_surface(): 按surface中的假名段拆分reading
     - 帽子を取る+ぼうしをとる→帽/ぼうし, を/(匹配消耗), 取/と, る/(送假名)
     - 核心思路：从左到右匹配surface中的假名段到reading中的对应位置，中间的reading属于前面的汉字段
  3. 混合变形处理：{xxx}含汉字时直接用作surface_display，用furigana splits映射辞书形注音
     - 帰った→用帰る的splits把"かえ"映射到"帰"位置
     - 面白かった→用面白い的splits把"おも"/"しろ"映射到"面"/"白"位置
     - {xxx}纯假名时（如{かぶって}）仍走derive_conjugated_surface推导

意义：
  - 假名注音从"基本不可用"提升到"大部分正确"，用户体验显著改善
  - 解决了EDRG数据中最常见的三类注音问题

新理解：
  - EDRG B行{xxx}标记有两种：纯假名（变形读音，如{かぶって}）和混合形（变形表面形，如{帰った}），比例约220k:124k，必须分别处理
  - EDRG的分词粒度不统一——有时"帽子を取る"是一个token，有时"帽子"+"を"+"取る"是三个token，reading拆分必须能处理这两种情况

【架构说明1】ViewPager2嵌套滑动
对应优化清单第1项

View层级树（从外到内）：

  LearnPage (Activity)
    └─ 外层VP2 (垂直, id=learn_page_vp2_container)          ← LearnPage.java:45
         ├─ pos 0: SearchPageFragment (搜索页)               ← LearnPageAdapter:27
         └─ pos 1: LearnPageFragment (学习页)                ← LearnPageAdapter:30
              └─ 中层VP2 (水平, id=learn_page_vp2_container)  ← fragment_learn_page.xml:9
                   ├─ pos 0: MainLearnPageFragment (单词概览)  ← MainLearnPageAdapter:27
                   │    显示：汉字+假名+释义+搭配+反义/近义词
                   │    交互：点击空白区域揭示释义 → 启用中层VP2滑动
                   └─ pos 1: ExtendedLearnPageFragment (详细释义) ← MainLearnPageAdapter:30
                        └─ 内层VP2 (水平, id=detailed_learn_page_view_pager)
                             └─ N个 ExtendedMeaningViewFragment (每个释义一个)
                                  └─ 最内层VP2 (水平, id=detailed_meaning_viewpager)
                                       └─ N个 ExtendedSentenceFragment (每个例句一个)

切换单词方式：底部按钮（preButton/nextButton）→ ViewModel.navigatePrevious/Next()
             不是滑动操作，按钮点击后中层VP2重置到pos 0

外层VP2垂直滑动：搜索页↔学习页切换，但ViewPager2ScrollController默认禁用手动滑动
                (setUserInputEnabled=false)，仅检测到明确垂直手势(dy>3*dx)时临时启用

滑动冲突解决机制（NestedScrollableHostBetween3Layers）：

  level=2 宿主包裹内层VP2，level=3 宿主包裹最内层VP2。
  核心原理：通过 requestDisallowInterceptTouchEvent 控制父VP2是否允许拦截事件。

  正常滑动时（子VP2能滑）：
    → requestParentDisallowIntercept(true) → 父VP2禁止拦截 → 子VP2独占事件

  滑到边界时（子VP2不能滑）：
    → requestParentDisallowIntercept(false) → 父VP2允许拦截 → 事件向上传递

  例句滑到边界→翻释义的关键逻辑（handleMoveEvent第247-250行）：
    1. level-3 host 调用 requestParentDisallowIntercept(false)
       → 沿父链传播：释义VP2、中层VP2、外层VP2 全部允许拦截
    2. level-2 host 调用 requestParentDisallowIntercept(true)
       → 沿父链传播：中层VP2、外层VP2 禁止拦截
    3. 净效果：只有释义VP2能拦截 → 翻到下一个释义
        （中层VP2不抢事件翻回概览页，外层VP2不误触垂直翻页）

【架构说明2】页面导航机制（ViewPager2Navigation）
对应优化清单第2项

从概览页点击释义跳转到详细页的导航流程：
  1. MeaningView点击释义 → turnToDetailPage(position)
  2. overviewDetailVp2.setCurrentItem(1) → 中层VP2切到ExtendedLearnPageFragment

  原因：LearnPageFragment:79覆盖了LearnPage.java:50的设置

清理机制：
  - Fragment.onDestroyView: setMeaningVp2(null) + clearPendingNavigation()
  - 按钮点击: clearPendingNavigation() 防止切换单词后过期意图

【架构说明3】导航校验机制（LearnPageViewModel.checkAndNavigate）
对应优化清单第3项

用户点击上一个/下一个按钮时的校验流程：
  1. navigatePrevious/Next → checkAndNavigate(targetId)
  2. databaseExecutor.execute → 同步查询wordDao.getWordByWordIdSync
  3. 单词有效 → currentWordId.postValue(targetId) → 数据管道刷新
  4. 单词无效 → toastMessage.postValue("已达词库末尾")

为什么用同步查询而非observeForever：
  - 导航校验是"查一次就走"，不需要观察数据变化
  - observeForever的removeObserver会因Transformations.map每次创建新实例而失败
  - 失败后observer永久挂在Room Dao LiveData上，数据库写入时误触发旧导航
  - 同步查询+postValue：零observer、零泄漏、postValue批处理合并连续点击
